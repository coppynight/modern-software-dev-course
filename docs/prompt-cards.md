# 六张可直接使用的协作卡片

替换方括号内容。只提供与任务相关且有权分享的资料。没有执行能力的聊天工具，要求它提出命令，由你运行并回传必要结果。

## 需求澄清

```text
用户是[谁]，希望在[场景]完成[动作]。
当前行为：[事实]。期望行为：[可观察结果]。
先列出会影响实现的歧义，再给最小范围和 5 条验收案例。
不清楚的地方标为假设。先不要改代码。
```

## 阅读代码

```text
请从[入口文件]追踪[用户动作]的数据流。
只读取[文件范围]，解释每层责任、输入输出与失败路径。
结论需指向具体函数；未找到的行为写未找到，不自行补全。
最后列出实现[小需求]可能需要改的最少文件。
```

## 小步实现

```text
按这份规格实现一个变化：[规格]。
保留现有公共接口，允许修改：[范围]。
先提出验证案例，再做最小修改，运行[真实检查命令]。
报告修改、执行结果和未验证项。不能执行时明确说明，不声称通过。
```

## 诊断失败

```text
期望：[结果]；实际：[结果]。
复现命令：[命令]；相关错误：[脱敏片段]。
先列最多三个可验证假设，按证据优先级排序。
对每个假设给出最小检查与预期信号，不要同时大改多个地方。
```

## 独立评审

```text
这是需求和最终 diff：[材料]。
先找行为错误、数据影响、边界和测试缺口，再给可选可读性建议。
每条意见包含位置、触发输入、影响和验证方法。
不要把未执行的猜测写成确定 bug；不要因代码作者的总结而跳过核验。
```

## 学习而不是代交

```text
我正在学习[概念]，目前理解是[自己的解释]。
请指出一个具体误解，给一个小实验和预期观察。
先给提示，不直接完成整份作业；我提交尝试后再帮我检查。
```

使用后在周报记录哪些部分实际改善了结果。没有普适的万能提示；卡片必须跟你的真实契约、文件和检查命令一致。
