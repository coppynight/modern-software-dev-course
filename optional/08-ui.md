# 选学 S08：从功能齐全到别人用得明白

[选学目录](README.md) · [返回主线](../lessons/05-deliver.md)

> 按需选学。下文的课时、练习和提交物只针对本专题，不计入主线完成要求；S00–S10 是选学编号。

**4–6 小时。** 目标：围绕一个用户任务改进完整流程，验证加载、空、成功和失败状态。交付：改版前后截图、交互状态表与一位试用者的观察记录。

## 核心讲解

用户不会从数据库表和函数名理解应用。他们关心「我能做什么」「刚才发生了什么」「下一步怎么办」。界面设计应从任务开始，再安排信息与操作。先让「输入笔记 → 看见候选 → 确认保存」顺畅，再考虑换配色。

一个按钮至少有可用、执行中、成功、失败几种状态。失败后用户输入是否保留？重复点击会不会保存两次？空列表是没有数据还是加载失败？这些是产品行为，也应该写进验收。

可访问性帮助更多人，也改善普通使用场景。输入需要标签；按钮需要可理解的名字；键盘焦点要可见；错误不只靠颜色表达；窄屏内容不能被截断。HTML 的语义元素通常比自行堆砌点击区域更可靠。

## 跟做：观察一次完整操作

启动应用，用键盘 Tab 走过添加任务、提取、候选添加。记录焦点顺序。将窗口缩到约 360px，输入一条 120 字符的长标题；再提交空格标题和没有任务标记的笔记。

打开浏览器开发者工具，在 Network 看 `POST /api/tasks` 的请求和响应。然后停止后端服务，再点击操作，观察反馈。测试完重启。网络故障和业务校验错误应分别理解，不能用同一句「输入不正确」掩盖所有问题。

## 必做：改造一条流程

选择「处理提取候选」：新增候选编辑、取消候选、确认后加入三个行为。先写状态表，再让助手改代码。现有单项「添加」能工作，但不能编辑预览；这是本周新增需求。

1. 画一个简单草图，明确用户一次需要判断的信息。
2. 为零候选、多个候选、空标题、超长标题、保存中、保存失败定义反馈。
3. 保留规则提取标签，若没有接模型，不把界面改名为「AI 智能提取」。
4. 实现并验证核心流程；用 `textContent` 或表单值传递文本，避免将笔记拼进 HTML。
5. 请一位朋友完成「把一段笔记变成两条任务」。不提前提示按钮位置，只记录卡点；若没有试用者，做自测并诚实标明。
6. 选择一个观察到的问题再修改。提交前后截图与原因，不能仅写「更高级」。

## 可选：多技术栈对照

原作业要求三个技术栈；本课程把它保留为进阶。已有一个完整版本后，用同一需求和同一测试清单构建第二个版本，第三个按精力选择。记录启动步骤、数据存储、依赖、手工修复、耗时及导出代码是否完整。

生成平台可以快速给出外观，但必须验证新增、查询、修改、删除、重启持久化和错误处理。截图漂亮、按钮没有接后端，不算同等功能。没有必要为对照购买三个套餐；学习重点是识别生成产物的边界。

## 验收与答案

至少验证桌面与窄屏、鼠标与键盘、成功与断网/停服、空与长文本。测试结果注明是人工还是自动，不把人工清单写成自动化覆盖。

自检：隐藏错误弹窗算修复体验问题吗？后端报错后清空用户笔记有什么后果？更换框架一定更现代吗？

答案：应解决或清楚反馈错误；会丢失输入并加重重试成本；现代开发关注可靠交付，框架本身不保证效果。
