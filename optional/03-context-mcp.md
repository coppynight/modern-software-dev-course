# 选学 S03：给助手正确的上下文和恰当的工具

[选学目录](README.md) · [返回主线](../lessons/02-build.md)

> 按需选学。下文的课时、练习和提交物只针对本专题，不计入主线完成要求；S00–S10 是选学编号。

**4–6 小时；真实 MCP 进阶另加 1–2 小时。** 目标：把一个模糊需求写成可执行规格，设计两项只读工具，理解 MCP 的边界。

## 核心讲解

「帮我完善项目」同时缺少范围与完成标准。上下文工程是选择这次任务需要的信息：哪些文件解释现状、哪些约束不能改变、哪些例子决定正确性、哪些历史决策仍有效。上下文越多不一定越好；过时方案、相互冲突的要求会干扰当前任务。

需求规格描述外部行为；设计文档描述怎么实现及为何选择；任务计划描述执行顺序。三者有关但不应混写。例如「用户能筛选未完成任务」是需求，「过滤放在数据库层」是设计，「先写过滤测试」是计划。

MCP 是连接宿主应用与外部能力的协议。宿主内的 client 与 server 协商能力；server 可暴露 tools、resources 和 prompts。它统一交换方式，不会自动提升模型能力，也不等同于完整授权。读任务和删除任务的风险不同，应通过不同接口和权限表达。

本地 STDIO 用进程的标准输入输出传协议消息，日志不能混入 stdout；写 stderr。网络 HTTP 模式还涉及身份、会话、权限与传输，先做本地有助于缩小问题。

## 跟做：把需求变成契约

模糊需求：「我只想看还没做完的事。」改写为：任务有全部、未完成、已完成三种视图；默认全部；切换视图不修改任务；空结果显示可理解的文案；刷新后的默认行为需明确。

打开 [需求模板](../templates/spec.md)，填入正常、空列表、切换后完成一项、非法筛选值四类场景。给助手只提供 `store.py`、相关路由与测试、这份规格。问它先列歧义，再提出最小方案，不要立即大改。

## 必做：两个工具的接口练习

```bash
python -m labs.task_tools
```

脚本对固定假数据调用 `list_tasks` 和 `task_stats`。这只是工具契约测试，不是 MCP 连接成功的证据。自己补充三个场景：合法筛选、非法值、空数据。写出每个工具的参数、输出、错误和副作用。

工具一返回有限条任务，工具二只返回总数与已完成数。为什么不能把整个数据库路径作为参数？因为调用方不需要任意读文件，固定数据来源更容易约束。

必做提交物：一页需求规格、相关文件清单、两个工具契约、三类场景的运行结果。接着把筛选需求实现到自己的应用，添加验证并更新 API 文档。若本周时间不足，可以把实现留到选学 S05，周报明确它仍是设计，不能勾选为已实现。

## 真实 MCP 进阶

按照 [MCP 实验说明](../labs/mcp/README.md) 安装隔离依赖。仓库提供两个只读工具的 SDK 适配器和本地客户端冒烟检查。先用固定数据跑通真实协议，再替换成你的小事板只读查询；这样能区分协议问题与业务问题。

随后选择一个自己有权调用的外部 API，使至少两项工具调用真实端点。规定连接超时、失败响应、空结果、速率限制以及要显示的有限字段。不得把任意 URL 作为自由参数后直接请求，也不要将用户令牌原样转发给不相关服务。

记录客户端版本、SDK 版本、工具发现结果和一次工具调用。完整进阶标准比基础线更高：真实 MCP + 外部 API + 异常路径。这里有两个阶段，别把固定数据的成功称作外部 API 已接入。

## 验收与答案

自检：把所有文件塞给助手是否最保险？普通 Python 函数有工具参数就算 MCP 吗？STDIO 服务为何不能用 `print()` 写运行日志？

答案：过多且冲突的内容可能降低理解质量；要经过协议握手、能力发现与调用才是 MCP；stdout 是协议通道，任意文本会破坏消息。
