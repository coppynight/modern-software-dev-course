# 选学 S04：把一次成功变成可重复的工作流

[选学目录](README.md) · [返回主线](../lessons/03-workflow.md)

> 按需选学。下文的课时、练习和提交物只针对本专题，不计入主线完成要求；S00–S10 是选学编号。

**4–6 小时。** 目标：设计并实际使用两套自动化流程，明确人和助手分别承担什么。交付：流程文件、两次执行证据、一次失败后的处理记录。

## 核心讲解

好的流程能减少反复解释，也能让失败停在可理解的位置。一个流程至少有输入、前置条件、动作、检查、输出和停止条件。仅写「认真测试」没有操作含义；写「运行课程检查，失败时列出失败测试，不声称完成」才可以验证。

项目说明应保存稳定事实：启动命令、文件边界、公共接口、检查方法。一次任务的临时需求放规格或 issue；大量执行日志放报告，不必全部进入助手每轮上下文。`AGENTS.md`、`CLAUDE.md` 等文件是否被自动读取取决于具体工具。课程模板本身不假定所有工具支持同一种发现方式。

自主程度是一系列选择：让助手提出方案、修改文件、执行命令、访问外部服务、发布结果。每一步带来的影响不同。个人练习中可以允许本地可撤销修改；如果将来接入共享数据和部署，就需要更明确的范围、权限与恢复方式。

## 跟做：拆解一个自动检查流程

阅读 `tools/check.py`，找出两个阶段：运行业务测试；检查课程链接、Python 语法与 JSON 数据。它通过进程退出码告诉外部系统成功或失败。退出码 0 表示成功，非 0 表示失败；终端显示绿色文字不是可靠的机器接口。

将这个流程写成自然语言：输入为仓库当前文件；输出为检查摘要与退出码；失败时停止，不自动删除测试；成功后仍由你检查功能差异。它就是后面自动化的最小契约。

## 必做：构建并使用两套流程

**流程 A：改动检查。** 从 [项目指令模板](../templates/project-instructions.md) 复制到自己的实验仓库，按实际工具命名，填真实命令。让助手检查第 2 或选学 S03功能，报告修改文件、失败测试与仍未验证的场景。无 Agent 时按清单手动执行。

**流程 B：接口文档同步。** 让助手阅读 `app/server.py`，对照 [API 文档](../docs/api.md)，找出接口、参数、状态码的差异。若有差异提出并应用最小文档修改，再以测试或真实请求核对。不能只由一个模型同时编造接口和文档然后互相印证。

每套流程至少真正执行一次，记录之前花在哪些重复步骤、现在仍需人工判断什么。没有运行过的 Markdown 只是计划，不叫自动化成果。为两套流程各加入一个退出条件，比如发现数据库迁移就暂停并单独设计。

## 角色分工实验

用三个独立会话或同一人的三个阶段扮演规划者、实现者、评审者。规划者交出规格和文件范围；实现者交出 diff 和运行证据；评审者仅根据需求与结果做判断。评审者应重新看需求，不只看实现者的自我总结。

可选的真实多 Agent 不是必须。先让串行交接稳定，再比较并行。两个助手同时编辑同一文件会产生覆盖和合并成本；并行收益要扣除协调与返工时间，不能把两个进度条当成效率翻倍。

## 验收与答案

每个流程都有输入、输出、实际执行、失败分支。周报中给出你拒绝或修正过的一条建议，并解释理由。

自检：把项目指令写得很长是否更可靠？测试绿色能否自动证明 PR 可合并？角色不同的两个 Agent 是否保证独立判断？

答案：可执行且与任务相关更重要；还要检查需求、范围与未覆盖风险；如果共享同一错误假设，角色名称不会消除偏差。
