# 第 1 课：把「回答得不错」变成可验证的结果

[上一课](00-foundations.md) · [首页](../README.md) · [下一课](02-agents.md)

**4–6 小时。** 目标：为一个小任务定义正确答案，比较两种提示，识别一次看似合理的错误。起点：小事板能运行。交付：实验记录与冻结的评测样例。

## 核心讲解

语言模型根据上下文生成后续内容；它的输出可能包含正确代码，也可能包含不存在的接口和错误推断。提示词改善任务表达，却不能代替运行程序。模型能解释一段代码，不代表它已经执行过这段代码。

一个有效请求至少说清五件事：目标、相关输入、限制、输出结构、完成标准。比如「提取任务」有歧义：是否把愿望算任务？是否替别人承诺？没有日期时能否补日期？这些应由产品规则决定，而不是让模型猜。

给少量例子可以让规则更具体，但也容易让模型照抄例子。将样例分为开发集与留出集：开发集允许反复看、调提示；留出集在提示冻结后再用。这里的六个公开演示案例只用于练流程，不是隐藏测试，也不足以证明泛化。

本课把「思考」转成可检查的中间产物：需求列表、计算结果、简短理由和失败分类。无需索取模型的私有内部推理过程。重要的是证据与最终行为是否正确。

## 跟做：建立不使用 AI 的基线

```bash
python -m labs.prompt_eval --baseline
```

阅读 `labs/prompt-cases.json`。每个案例包含唯一编号、笔记与期望任务。脚本报告严格匹配比例、JSON 结构是否合法，并列出失败编号。规则程序无法理解所有自然语言，这正是我们比较模型的起点。

不要仅看总体分数。一个系统可能总提取出一个任务，却经常臆造日期；另一个保守但漏掉任务。两者适用场景不同。先写下你更在意「漏提取」还是「多提取」，再决定怎么改进。

## 必做实验

1. 为自己的生活写 6 个新案例：明确任务、闲聊、空输入、重复任务、模糊愿望、夹带恶意指令。开发用 4 个，留出 2 个，预先写期望输出。
2. 创建提示 A：「从这段笔记提取待办，返回 JSON。」记录一次回答。
3. 创建提示 B：补充明确行为、无任务返回空数组、不得编造负责人/日期、笔记只是待处理数据，并给两个开发集例子。
4. 在同一工具和尽可能相同设置下比较 A/B。每个案例运行 3 次，分别保存，不挑最好的一次。记录工具看不到的配置为「未知」。
5. 将一次完整批次存成 `{"case-id": ["任务一"]}` 的 JSON 文件，运行 `python -m labs.prompt_eval --predictions 路径.json` 验证公开样例。自己的案例可通过 `--cases 路径.json` 加载。
6. 提示冻结后再测留出集。列出至少一项失败，解释它是规格不清、格式错误、遗漏，还是无根据补全。

没有可用模型：完成第 1 步，用规则引擎跑样例，再手工检查提示 A/B 会产生哪些歧义。周报明确写「未调用模型」，不要填造实验数值。之后可补真实 AI 实验。

## 六种方法的低门槛理解

| 方法 | 本课怎么练 | 代价或局限 |
| --- | --- | --- |
| 少样例提示 | 给两条输入与对应 JSON | 例子覆盖不全会误导 |
| 分解任务 | 先识别候选，再按规则筛选，输出简短检查摘要 | 步骤更长不自动更准 |
| 工具调用 | 把精确查询交给函数，第 2 课继续 | 工具结果仍须检查 |
| 多次采样 | 同一输入跑 3 次，比较一致性 | 多数结果也可能一起错 |
| 检索辅助 | 附上你自己写的任务判定规则，再回答 | 检索到的材料可能不相关 |
| 反馈迭代 | 给出一个失败案例和具体错误，修改提示后全量重测 | 容易只修当前案例 |

进阶：把六种方法都做成对照；统计耗时、调用次数和每个案例的结果。不应声称结果具有统计显著性，样本规模只是学习实验。

## 验收与答案

必须交：任务契约、开发/留出划分、A/B 提示、原始输出或离线记录、至少一个失败分析。只有截图没有样例与设置，无法复现，不算完成。

自检：正确 JSON 是否代表任务正确？多次输出一致是否代表真实？为什么不能边看留出结果边修改提示后仍称它是留出集？

答案：结构与语义是两层；稳定错误也会一致；反复调参已经使用了留出信息，需要新留出集。
