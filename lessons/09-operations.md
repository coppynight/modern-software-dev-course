# 第 9 课：上线思维，从本地故障演练开始

[上一课](08-ui.md) · [首页](../README.md) · [下一课](10-capstone.md)

**4–6 小时。** 目标：根据日志定位一次故障，区分恢复服务与寻找根因，验证恢复后数据仍可用。交付：指标摘要、演练时间线、恢复手册。

## 核心讲解

交付不是「我电脑能跑」。其他人需要知道如何启动、怎样判断健康、失败找什么证据、怎样回到稳定状态。可观测性让系统状态可理解：日志记录离散事件，指标汇总数量与耗时，链路帮助连接一次请求跨越的组件。

小事板每次请求记录请求编号、方法、路由、状态码与耗时。它故意不记录标题和笔记正文。请求编号可帮助关联用户报告，但当前没有分布式链路，不要把一串编号称为完整 tracing。

错误率先定义分母。本课分别统计 4xx 与 5xx，前者常是被拒绝的输入，后者表示服务端问题。p95 是按耗时排序后第 95 百分位，不是平均值。小样本的 p95 会很不稳定，适合学习计算，不适合宣称性能达标。

## 跟做：采集并分析

在终端一运行：

```bash
python -m app.server 2> app.log
```

浏览器做 10 次左右操作，包含合法创建、空标题、不存在的任务。停止服务。在同一根目录运行：

```bash
python tools/log_summary.py app.log
```

PowerShell 不同版本可能采用不同重定向编码，脚本支持 UTF-8 与带 BOM 的 UTF-16。若读取失败，使用编辑器另存为 UTF-8。检查输出的请求数、4xx、5xx、p95；为每类找到一条原始证据。日志默认不进 Git。

`/health` 只证明 HTTP 进程可响应，不访问数据库；因此它不是完整就绪检查。扩展任务可以增加单独的 readiness 检查，并解释它是否会对数据产生写入。

## 必做：一次可恢复的本地演练

只用练习数据。在开始前停止服务，复制 `data/tasks.db` 到自己的备份目录，记录当前 Git 提交与任务数量。数据库复制要在服务停止后进行；未来若启用 WAL，需要更合适的备份方法，不能盲拷单文件。

1. 记录正常状态：启动成功、任务列表可读、新增可保存。
2. 模拟进程退出：Ctrl+C，浏览器再提交，记录实际反馈与时间。
3. 根据恢复手册重启，确认原数据仍存在，再做一次新增、修改、删除。
4. 可选模拟一次代码回归：在独立分支改坏提取逻辑，确认测试能抓住它，用 `git revert` 撤回那个已提交的变更，再验证。
5. 写 [事故记录](../templates/incident.md)：症状、影响、证据、假设、操作、验证、改进。

代码回滚不等于数据回滚。如果新代码改变表结构，旧代码可能无法读取；先恢复服务的决策必须考虑数据兼容性。本课不要求实现数据库迁移，但必须在报告中说明这一限制。

## Agent 在运维中的位置

可以让助手整理日志、提出待验证假设、生成排查命令。先验证命令作用，再执行。一次 500 不足以自动判断根因；不要让没有证据的猜测直接触发删除数据库、重建服务或覆盖配置。

每项行动写出成功信号与停止条件。比如「重启后健康接口恢复，但任务列表失败」意味着进程恢复而业务未恢复，应继续查数据库，不能宣称事故结束。

## 验收与答案

你或同伴应能按手册从停止状态恢复，在不丢练习数据的情况下完成核心操作。交真实时间线，不把演练故障写成线上事故。

自检：健康接口 200 是否等于用户任务正常？平均延迟低是否排除少量慢请求？撤回代码提交是否能恢复误删数据？

答案：不一定；不能；不能，需要事先备份与恢复验证。
