# 1. 把需求交代清楚

[首页](../README.md) · [下一单元](02-build.md)

**约 1–2 小时。产出：半页任务卡，能让别人判断做对没有。**

## 三个要点

1. **用行为定义完成。**「完善筛选」无法验收；「选择未完成后只显示未完成项，空结果有提示」可以。
2. **只给相关上下文。**先提供需求、相关入口、接口约束和测试。无关文件、过时方案与整段聊天历史会增加干扰。
3. **提示要靠结果比较。**更长的提示不自动更好。固定案例，比较遗漏、误解与无根据补全。

规格描述用户看到什么，设计解释如何实现，计划说明先做什么。先写清规格，再让助手提出方案。

## 动手：定义筛选功能

在 [任务卡](../templates/task-card.md) 写下以下约定，按你的项目调整：

| 输入或操作 | 预期 |
| --- | --- |
| 不传筛选条件 | 默认显示全部任务 |
| `status=open` / `done` | 分别返回未完成 / 已完成任务 |
| `status=all` | 返回全部任务，顺序保持不变 |
| 非法 status | 返回明确的输入错误，不静默当作全部 |
| 没有匹配项 | 显示空状态；切换筛选不修改数据 |

先给助手一句模糊请求「帮我给任务列表加筛选」，只让它提方案。再在新会话提供上述规格、相关文件和范围。比较两次方案是否遗漏默认值、错误输入或数据副作用，选出更可执行的一份。

```text
请根据这份规格和相关文件，先指出影响实现的歧义，
再给最小修改范围和验证方法。未确定的部分标为假设。
本轮先不改代码。
```

产品行为由你决定，不把模型偏好自动升级为需求。冻结范围：只做筛选，不顺带加登录、分类、云同步。

**完成标准：**正常、边界、失败三类结果明确；计划指向真实文件；能指出两种请求方式造成的一项具体差异。
