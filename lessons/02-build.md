# 2. 让 Agent 做小步实现

[上一单元](01-spec.md) · [首页](../README.md) · [下一单元](03-workflow.md)

**约 2–3 小时。产出：筛选功能的第一版和实际验证结果。**

## 看清一次循环

编码 Agent 由模型、工具执行器、上下文状态与停止条件组成。模型建议调用工具，执行器真正读写文件或运行命令，结果返回后再决定下一步。**「已经修好了」是陈述，测试进程的结果才是执行证据。**

权限和范围决定出错时会影响什么。本次只需读相关代码、修改功能与测试、运行本地检查；不需要访问个人文件或发布服务。一次只解决一个明确失败，避免反复让助手「全部重写」。

## 动手：分两步完成

1. 让助手按任务卡实现接口筛选和测试。起始项目已有 CRUD，只需增加查询条件、输入校验与过滤，不重建整个应用。
2. 看 diff 并运行测试；确认 `all/open/done` 与非法值都有证据。再加页面的三个筛选入口，验证界面与接口一致。

```text
按任务卡先实现后端筛选与相关测试，再接入页面。
沿用现有结构，只修改本需求涉及的文件。
每步运行验证并报告真实结果；无法执行的部分明确列出。
遇到失败先定位原因，不同时改多个无关地方。
```

在任务卡保留一条「调用 → 结果 → 后续处理」。遇到失败就记录恢复；没有失败可以在自己的实验分支临时改坏一个预期，确认检查能发现，再恢复。查看最终 diff，确保没有为通过检查而弱化断言。

附带项目运行 `python3 tools/check.py`；其他项目使用等价命令。只有聊天工具时由你执行，不把生成的命令当成已运行。

## 工具与 MCP

工具应有明确参数、结果、错误和副作用。`list_tasks(status)` 比任意 shell 命令更容易约束。MCP 统一宿主接入外部能力的协议，不自动提供业务正确性或完整权限控制。当前功能不需要外部能力，就不必为了使用 MCP 而接入它。

**完成标准：**功能可运行；至少一条调用链有证据；测试与任务卡一致，能解释关键修改。
