# 第 2 课：理解模型、工具和 Agent 循环

[上一课](01-prompting.md) · [首页](../README.md) · [下一课](03-context-mcp.md)

**4–6 小时。** 目标：区分模型建议、工具执行与真实结果；从一个小功能体验可控的自动化。交付：轨迹表、变更与验证结果。

## 核心讲解

聊天模型通常生成文本；编码 Agent 在模型之外还包含工具执行器、历史状态、权限约束和停止条件。模型可能提出「调用测试」，实际进程由工具执行，stdout、stderr、退出码作为新输入返回模型。循环继续，直到满足退出条件或者达到预算。

一个常见误判是把「我已经修好了」当作事实。先看是否有对应工具调用，再看退出码，最后确认测试确实覆盖需求。模型的陈述和机器观测要分开记录。

工具不是任意命令的别名。`list_tasks(done=False)` 比 `run_anything(command)` 更窄、更容易验证。参数类型、默认值、输出结构和错误含义，共同决定模型能否正确使用它。限制轮数、输出长度与可调用工具，是限制故障扩散的方法。

## 跟做：不用模型也能看见一次循环

```bash
python -m labs.agent_trace
```

这是**脚本生成的教学轨迹，不是模型实际决策，也不是 MCP**。它先用错误参数调用一个只读工具，收到错误后再用合法参数调用，最后结束。找到每一步的 `kind`、输入、输出和停止原因，手工画出「建议调用 → 参数校验 → 执行 → 返回」的顺序。

修改输入令所有调用都失败，确认循环仍在限定步数停止。一个循环能自动恢复一次错误，不代表它能无限期自行工作。

## 必做：让小事板支持英文小写标记

需求：现有 `TODO:` 大写有效，增加 `todo:` 和 `Todo:`；中文与列表标记保持现状，不把单词内部的 `todo:` 误识别成任务。

1. 先不改代码，让助手或自己读 `domain.py` 与现有测试。写出需修改的文件和 4 个验收案例。
2. 新增案例：`todo: read`、`Todo: read`、前导空格、`sometodo: read`。最后一个期望为空。
3. 只改提取逻辑与对应测试；保留原输入中文内容，不把整个标题变成小写。
4. 运行 `python tools/check.py`，记录失败与修复过程，查看 diff 中是否出现无关改动。
5. 在网页验证：预览正确、添加成功、刷新仍在。

使用真实编码 Agent 的学员：把工具调用分为读文件、改文件、执行、网络访问四类；每类写出用途。未出现的行为写「未观察」，不要根据产品宣传推断。

无 Agent 的学员：手动按同样步骤执行，把发给助手的请求和自己执行的命令分两栏记录。

## 完整 AI 线：可替换的提取引擎

原作业的核心之一是将规则提取升级为模型提取。先新增独立接口 `extract_with_model(note, provider)`，`provider` 是你已有工具/API 的适配层，别让数据库知道模型厂商。规定超时、无效 JSON、超长输出和不可用时的行为。

测试中用可控的假 provider 返回成功、错误格式、异常；这叫桩或替身，验证调用契约。再用真实 provider 跑第 1 周评测，单独记录模型结果。桩测试通过不能作为模型能力证据。API 密钥放本地环境，任何网页脚本和提交文件都不保存密钥。

先展示候选、由用户确认再保存，避免模型误解直接污染任务列表。模型不可用时应提示失败或明确退回规则引擎，不能假装使用了 AI。

## 验收与答案

交至少一条完整成功链、一条失败链、功能 diff 与测试输出。你要能说明哪部分做决定、哪部分执行、凭什么停止。

自检：模型发出工具请求时，工具一定执行了吗？假 provider 通过可以证明提取准确吗？把失败日志继续提供给模型是否总有益？

答案：还要过参数、权限与执行层；只能证明本地契约；日志可能含无关信息或敏感内容，应选取与故障相关的最小片段。
