# 3. 建立可重复工作流

[上一单元](02-build.md) · [首页](../README.md) · [下一单元](04-review.md)

**约 1–2 小时。产出：简短项目说明、一个反复可用的检查入口。**

## 只沉淀稳定信息

项目说明保留启动命令、目录职责、验证入口和修改边界；本次需求放任务卡；日志保留必要证据。不要把所有历史塞进助手每轮上下文。

流程要说清「输入 → 动作 → 成功信号 → 失败处理」。例如「运行检查，失败就报告失败项并停止，成功后审阅最终 diff」。只写「认真测试」无法执行。

## 动手：让新会话接得住

1. 用 [项目说明模板](../templates/project-instructions.md) 写不超过一页的说明，填入实际验证过的命令。按所用工具的规则保存或主动提供，不能假定所有工具都自动读取同名文件。
2. 开一个新会话，请助手仅凭任务卡和项目说明，检查筛选功能、同步 API 文档并执行验证。
3. 把仍需重复解释的关键信息补入说明，再确认流程可重复。

附带项目已有 `tools/check.py` 和 GitHub Actions，复用即可；自有项目选一个等价入口。以退出码和实际测试结果判断成功；检查失败后继续输出「完成」属于流程问题。

```text
读取项目说明与任务卡，核对筛选接口和文档是否一致。
如需修改，只更新相关文档；运行已约定的检查。
输出发现、实际运行结果、仍需人工核验项。
```

多 Agent 的价值来自任务可分、上下文可交接，不来自数量。这个小功能先用串行流程完成；需要并行时再拆文件责任和分支，评估合并与返工成本。

**完成标准：**新会话能找到正确入口；检查可以重复运行；文档与行为一致；任务卡记录一次真实执行，不另交长报告。
